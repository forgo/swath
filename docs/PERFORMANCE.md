## 1. Method, before numbers

1. **One recipe per instrument.** Each class of measurement has exactly one entry point
   (`just perf-i2p`, `just bench-baseline`, `just load`, `just load-temporal`,
   `just perf-referencer`). What CI or a
   reviewer runs is what produced the tables here — there is no separate "benchmark script for the
   docs".
2. **Committed artifacts are the ground truth.** The recipes distill raw output into JSON under
   `docs/perf/`. A PR that changes a number changes a committed artifact, so the diff *is* the
   claim review. The tables in this document — and every inline `number:<key>` headline figure
   across the docs — are generated from those artifacts by `just perf-doc`; the prose is
   hand-written.
3. **Enforcement over aspiration.** The headline number (ingest-to-pixel) is not just measured —
   the same typed e2e harness that measures it asserts it under a budget on every commit
   (`crates/swath-e2e`, `I2P_BUDGET_MS`). The load and bench baselines are regression evidence:
   re-run, diff, explain movement in the PR.

## 4. Ingest-to-pixel (the headline)

The north-star metric (REQUIREMENTS §3): time from *"a new granule arrives"* to *"a correct tile is
visible on the map."* Measured end to end through the real stack — filedrop event, STAC
registration, first live render of a never-before-seen tile — by the same harness that verifies the
tile's pixels against goldens.

|---|---:|---:|
| ingest_to_pixel_ms | 646 ms | 10000 ms |

**Enforcement.** The number is not a brochure figure: `just e2e` asserts `ingest_to_pixel_ms` under
the 10,000 ms budget on every commit (`crates/swath-e2e/src/main.rs`, `I2P_BUDGET_MS`), and CI runs
that harness. The budget is deliberately ~20× above measured values so it catches structural
regressions (an accidental poll interval, a batch step) rather than runner noise; tightening it is a
deliberate, visible act. Context from prior runs of the same harness: 297 ms and 801 ms locally,
535 ms in CI.

Single-request tile latency under no load is visible in the load table below (cold live renders:

## 7. Referencer: the historic "40×" and "14 ms" claims, re-run

**Provenance of the claims.** Prototype 0001 (referencer bake-off, concluded 2026-08-08, immutable)
measured legacy-format virtual-reference generation on the VNP09GA granule: *"referencer-rs 29 ms
cold / 14 ms warm; virtualizarr sidecar 876 ms cold / ~556–574 ms warm … Rust ≤ sidecar by ~40×
warm."* Those numbers came from the prototype's dev-profile harness timing the Rust generator
**in-process** while timing the sidecar **as a subprocess** (Python spawn + import included).

**Re-measurement on this tree.** The prototype code is frozen; what ships is the production
generator (`swath ingest reference`) and the promoted conformance sidecar
(`python/sidecars/referencer`). `just perf-referencer` measures both the same way — full-process
wall clock, release profile, same granule — which is *less* flattering to Rust than the prototype's
in-process timing (the Rust figure now includes process spawn, CLI startup, and writing the 201 KB
manifest):

```bash
just perf-referencer   # fetches the pinned granule if absent (needs Earthdata netrc)
```

**Verdicts, claim by claim** (this run: `docs/perf/referencer-baseline.json`, all 10 raw samples
in the artifact):

- **"14 ms warm" — reproduces.** Warm median <!-- number:ref-warm-ms -->13.8 ms<!-- /number:ref-warm-ms --> for the production release binary,
  full-process (the prototype's 14 ms was in-process, dev profile — the release-profile speedup
  and the added process overhead happen to cancel).
- **"~40× warm" — reproduces.** Sidecar warm median <!-- number:ref-sidecar-warm-ms -->545.6 ms<!-- /number:ref-sidecar-warm-ms --> / Rust <!-- number:ref-warm-ms -->13.8 ms<!-- /number:ref-warm-ms --> = **<!-- number:ref-ratio -->39.5×<!-- /number:ref-ratio -->**, squarely
  in line with the prototype's ~40× (its sidecar range was ~556–574 ms; ours is 535–557 ms).
- **The cold numbers are NOT comparable to the prototype's and we don't headline them.** This
  run's cold figures are first-invocation-after-build effects: the Rust 456 ms first run is
  dominated by first-touch of a freshly linked ~4.5 MB binary plus macOS code-signature
  verification; the sidecar's 13.3 s first run is dominated by one-time bytecode compilation of a
  fresh `uv sync` venv. The prototype's "29 ms cold / 876 ms cold" were first runs against an
  already-exercised binary and venv. Steady-state (warm) is the operationally meaningful figure
  for a per-granule ingest step, and it is the one we claim.

Both generators emit byte-range-equivalent manifests for this granule — that equivalence is the
gated conformance test (`just test-referencer`), so the speed comparison is between two
implementations producing verified-identical output.

**Honest accounting of the ratio.** The sidecar's per-invocation cost is dominated by Python
interpreter + import time, and the production ingest path runs the generator per granule as a
process — so per-invocation is the operationally honest unit. But stated plainly: this is an
architecture result (no interpreter, no warm-up, 4.5 MB static binary vs a ~273 MB venv), not a
claim that Rust scans HDF5 chunk indexes <!-- number:ref-ratio-approx -->~40×<!-- /number:ref-ratio-approx --> faster than h5py once Python is already warm.

## 8. Temporal frame-serving and overview-backed tiles

The M7 measurement (`just load-temporal`): the time slider's serving path (ADR 0015, issue #223)
and the materialized overview path (`swath materialize`, issues #183/#218). Environment: the §2
laptop and compose stack (the artifact records its own machine stamp), with one addition to the
serve dataset — the six-date Park Fire fixture series (`tests/fixtures/README.md`, 24 COGs,
~2.3 MB, one 256×256-pixel window across six 2024 acquisitions) is dropped mid-run through the
same filedrop path the e2e uses, and is cataloged as its own dataset. Scenario parameters and
rationale: `tests/load/temporal.py`; orchestration: `tests/load/temporal.sh`. Every request's
render decision is recorded from the `x-swath-trace` header, and the report *fails* unless the
decision mix is exactly what each scenario is defined by — the latencies below are proven to be
the paths they claim to measure, not assumed.

**(d) Animation frames.** The frame loop a time-slider scrub replays: every interior z14 tile of
the fire footprint (the animation viewport), requested with `datetime=<acquisition instant>` for
each of the six dates in order. Cold — a fresh tile cache, so every dated frame is a live
render — p50 <!-- number:frame-cold-p50-approx -->~350 ms<!-- /number:frame-cold-p50-approx -->
per tile; the same loop again is all granule-scoped cache hits at p50
<!-- number:frame-hot-p50-approx -->~8 ms<!-- /number:frame-hot-p50-approx --> — the temporal cache
identity (granule id, not the datetime string) is what makes a replayed animation this cheap.

**(e) The overview ladder.** One tile per zoom rung, rendered repeatedly with the tile cache
cleared before every request, so each rung measures its *render* path. At z12 the planner runs
full-resolution live (p50 <!-- number:ov-live-p50-approx -->~260 ms<!-- /number:ov-live-p50-approx -->).
Before materialization, the z10 rung already serves the fixtures' embedded ×2 overview; after
`swath materialize` (<!-- number:materialize-ms -->578 ms<!-- /number:materialize-ms --> for every
layer of both datasets, run mid-scenario) the same z10 tile plans the materialized ×4 pyramid
level at p50 <!-- number:ov-pyramid-p50-approx -->~130 ms<!-- /number:ov-pyramid-p50-approx -->. The
overview *level* served by each rung is pinned from the SSE trace envelopes (the header's
`decision` says only `overview`; the envelope carries `{"overview":{"level":…}}`).

## 9. What we don't claim

Bounded honesty, in the spirit of the requirements' "reports it continuously and honestly":

- **Fixture scale.** Serve-path numbers are measured over ~1.4 MB of committed HLS fixtures and
  one 8 MB VNP09GA granule. No claims about multi-terabyte catalogs, thousands of layers, or
  granules that dwarf RAM.
- **Single node, loopback.** One container on one laptop, `localhost` HTTP. No network latency, no
  TLS termination, no CDN, no horizontal scaling, no claims about behavior behind a real ingress.
- **Local storage.** Sources and cache are local disk (the e2e stack's MinIO is loopback too). No
  claims about S3 cross-region byte-range latency on the virtual-reference read path.
- **Tested concurrency only.** Load scenarios go up to c=32 for seconds-to-minutes windows. No
  claims about sustained multi-hour load, connection counts beyond those tested, or fairness under
  overload.
- **Microbenches are isolated stages.** Criterion numbers measure each stage alone on a quiet
  machine; they do not include queueing, cache contention, or concurrent-warp interference (that is
  what §6 samples).
- **One machine, uncontrolled.** A developer laptop, thermals and background load not isolated.
  Cross-machine comparisons of absolute numbers are not supported; diff same-machine baselines.
- **The <!-- number:ref-ratio-approx -->~40×<!-- /number:ref-ratio-approx --> ratio is per-invocation, one granule, one format.** See §7's accounting — it includes
  Python startup by design, and was measured on a single HDF-EOS5 granule.
- **CI runners are slower and noisier.** The enforcement budget (10 s) is sized for that; the
  measured numbers here are laptop numbers.

Several of these gaps are intended future work, not permanent posture — real-ingress (CDN/TLS)
behavior, multi-node scale, and larger-than-fixture datasets are on the M7+ candidate list in
[`ROADMAP.md`](ROADMAP.md).
